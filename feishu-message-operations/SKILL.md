# 飞书消息推送

把每次推送当成一次可审阅、可追踪、可安全恢复的发送活动。开发、部署、页面加载和生成预览都不等于正式发送。

## 面向用户

- 业务运营：选择内容和接收对象，预览并确认正式发送。
- 系统管理员：管理飞书应用、权限、租户、机器人和发送主体。
- 开发者或 Agent：实现、排查或复用消息推送能力，并提供审计和失败恢复。

## 适用场景

- 给当前用户发送一张测试卡片。
- 给选定人员逐人发送单聊消息。
- 在指定群聊直接发送消息。
- 读取完整群成员后，向每位成员分别私发。
- 使用不同企业或租户的应用分别发送。
- 发送 Skill 上新、活动通知、任务提醒、异常提醒或定期摘要。
- 查看逐人、逐卡的发送结果，或只重试明确失败的对象。
- 把临时脚本改造成长期可复用的消息运营入口。

## 使用方式

让用户尽量提供以下信息；缺少的内容先从当前项目和飞书只读查询，不要要求用户填写系统已经知道的数据。

```text
消息目的：
发送内容或数据源：
发送主体/企业：
接收方式：本人测试 / 人员单聊 / 群聊直发 / 群成员逐人私发
接收对象：
排除对象：
发送时间：现在 / 指定时间
是否只生成预览：
```

可直接使用以下表达：

- “使用 $feishu-message-operations，先把这张卡片发给我测试。”
- “使用 $feishu-message-operations，给这个群的同租户成员逐人私发，跨租户先保留。”
- “使用 $feishu-message-operations，把这次 Skill 上新做成可长期重复使用的运营功能。”
- “使用 $feishu-message-operations，核对上次发送结果，只重试失败对象。”

## 标准操作流

### 1. 明确发送任务

确认以下事实：

- 谁发送：实际操作人、飞书应用、企业和租户。
- 为什么发送：接收人为什么需要这条消息，以及需要做什么。
- 发什么：事实来源、卡片版本、按钮链接和完整文案。
- 发给谁：目标类型、最终名单、排除项和跨租户对象。
- 何时算成功：预计消息数、需要保存的结果和验收方式。

用户只要求诊断、评估或预览时，保持只读，不正式发送。

### 2. 读取项目边界

先读取当前项目的 `AGENTS.md`、运行手册、消息运营规则和现有实现。优先复用正式运营入口，不新建一次性发送脚本。

只有同时满足以下条件时，才读取 [AI Land 项目路由](references/ailand.md)：

- 当前项目是 AI Land；
- 任务涉及批量人员单聊、群聊发送、群成员逐人私发、多主体/跨租户、正式发送恢复与重试，或修改这些能力。

普通 AI Land 任务和单张卡片发给当前用户本人不读取该参考。

### 3. 锁定发送主体

选择实际发送应用，并检查：

- 应用处于启用状态，凭证属于目标租户。
- 操作人具有消息运营权限。
- 机器人具备发送消息所需权限，并在目标群内或能访问目标群。
- 读取群成员或通讯录所需权限已经开通。
- 目标标识与应用口径一致。

不要混用以下标识：

- `open_id`：通常受应用和租户口径约束。
- `user_id`：租户内人员标识，按接口要求使用。
- `chat_id`：群聊标识，只用于群聊目标。
- `message_id`：发送成功后保存，用于核对具体消息。

跨租户对象不要硬发。按租户拆分，切换到对应应用后重新确认发送；暂时不能发送的对象保留为待处理范围并写明原因。

### 4. 生成并检查消息

从事实源重新生成消息，不依赖旧截图、过期缓存或手工复制结果。

- 保持字段含义真实，不把版本号当 Skill 编号，不把点击称为下载。
- 解析飞书 Base 富文本和超链接字段时，同时读取文字与真实 URL。
- 按用户要求展示完整内容；不要静默截断。内容确实过长时，先拆分结构或征求用户同意。
- 检查标题、正文、分栏、按钮文案、按钮链接、发送方和预期动作。
- 为最终卡片生成稳定指纹。卡片或链接改变后，旧确认立即失效。

### 5. 解析并冻结受众

根据发送方式处理：

- 本人测试：接收人只能从当前登录态取得，不接受前端传入其他人员 ID。
- 人员单聊：逐人校验账号状态、租户和消息接收标识。
- 群聊直发：校验应用可见该群，接收目标是 `chat_id`。
- 群成员逐人私发：完整分页读取群成员，再按应用租户拆分同租户与跨租户对象。

完整保存最终名单、人数、排除项、跨租户范围、数据来源、采集时间和分页完整性。不能把“本页没看到”当作成员不存在。

遇到以下情况立即停止：

- 群成员分页不完整或人数与人工核对值不一致。
- 同租户同名冲突且缺少稳定人员 ID。
- 接收人已停用、应用不可见或租户不匹配。
- 发送主体、卡片指纹或受众在确认后发生变化。

### 6. 先预览，再确认

预览不得触发正式发送。本人测试和正式发送使用独立请求。

正式发送前向用户回显：

- 实际操作人和发送主体。
- 完整卡片或消息内容及所有按钮链接。
- 接收方式、最终人员或群聊、人数和排除项。
- 跨租户待处理人数。
- 卡片数量与预计总发送条数。

要求用户对这次内容和这次名单做明确确认。名单、内容或主体改变后重新确认。项目已有页面二次确认时，不用接口或脚本绕过页面。

### 7. 建立审计和幂等键

在调用飞书前先建立发送批次审计；审计建立失败时不发送。

为每个“活动 + 卡片 + 租户 + 接收目标”生成稳定幂等键。逐目标记录状态：

- `started`：已经进入发送调用，结果尚未确认。
- `sent`：发送成功，保存 `message_id` 和发送时间。
- `failed`：发送失败，保存错误码和可读原因。
- `deferred`：因跨租户、权限或资料缺失暂不发送。

不要把整批只有一个成功标记当作逐人成功证据。

### 8. 执行正式发送

只发送确认快照内的对象。

- 群聊直发按群记录结果。
- 人员单聊和群成员私发按人、按卡记录结果。
- 控制并发和速率，保留飞书原始错误码。
- 某个目标失败时不要让已经成功的目标再次接收。
- 进程中断时保留 `started`，不要自动改成失败。

### 9. 核对结果并安全重试

发送后报告：活动编号、发送主体、总目标数、成功数、失败数、待核对数、跨租户待处理数和 `message_id` 保存情况。

重试时：

- 只选择明确为 `failed` 的目标，并再次确认。
- 永远跳过 `sent`。
- 对 `started` 先查实收、操作日志或消息状态，不能直接重发。
- 受众或卡片改变时新建活动，不复用旧确认。

未明确要求时，不查询已读未读状态，也不自动补推未读人员。若要启用未读补推，单独定义权限、查询周期、频控、停止条件和去重规则。

## 工具选择

- 已有消息运营页面和服务端接口时，优先使用它们。
- 需要操作飞书消息和群成员时，配合 `lark-im`；需要解析人员身份时，配合 `lark-contact`；需要认证与应用口径时，配合 `lark-shared`。
- 现有 CLI 没封装所需能力时，先查飞书官方 OpenAPI；不要据此断言平台不支持。
- 执行任何正式写入前，先读回最终应用、群聊和人数。

## 交付格式

发送前用以下格式汇报：

```text
发送主体：
消息内容：
发送方式：
最终对象：
排除/待处理：
卡片数 × 接收人数：
预计消息数：
审计与重试规则：
等待确认：是
```

发送后用以下格式汇报：

```text
活动编号：
发送主体：
成功：
失败：
待核对：
跨租户待处理：
message_id：已保存 / 未完整保存
下一步：无需处理 / 核对待确认 / 人工重试失败项
```
